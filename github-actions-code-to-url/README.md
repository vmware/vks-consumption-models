# VKS Zero-Trust "Code-to-URL" GitHub Actions Pipeline

This repository contains a modular, enterprise-grade Continuous Integration and Continuous Deployment (CI/CD) pipeline built with GitHub Actions, OpenID Connect (OIDC), Helm, and Istio Service Mesh, running on a **VKS** cluster.

The core objective is to achieve a true **Code-to-URL** developer workflow: every time a developer opens or updates a Pull Request, an isolated, ephemeral preview environment is automatically compiled, securely routed via Istio, and verified with zero long-lived secrets.

---

## Architecture Overview

1. **Trigger Engine:** GitHub Actions listens selectively to branch states (`main` pushes vs. targeted feature branch PR lifecycles).
2. **Secure Compilation:** A self-hosted runner executes multi-stage Docker builds utilizing native caching layers (`type=gha`) and pushes container images to the GitHub Container Registry (GHCR).
3. **Zero-Trust Handshake:** The runner fetches a short-lived OIDC JWT token from GitHub and presents it to the VKS control plane API. 
4. **Dynamic Authorization:** The VKS control plane uses a Common Expression Language (CEL) claim mapping to translate incoming tokens into a generic, fork-reusable Kubernetes group string (`github-org:<repository_owner>`).
5. **Traffic Routing:** Helm deploys the application service instances, and `envsubst` dynamically builds customized Istio `VirtualService` and `Gateway` definitions matching the precise context environment (`pr-<number>` or `main`).

## Pipeline Prerequisites


### 1. Dedicated Self-Hosted Runner

Because this workflow relies on direct, zero-trust network access to internal control planes, a self-hosted GitHub Actions runner must be pre-configured and active within a network segment that has route access to the target VKS API endpoint. The runner handles the OIDC token exchange without exposing your API server to the public internet.

Follow these steps to download, configure, and install the GitHub Actions runner binaries on your Ubuntu VM.

```bash
# Create a folder for the runner
mkdir actions-runner && cd actions-runner

# Download the latest runner package (adjust the version if needed)
curl -o actions-runner-linux-x64-2.334.0.tar.gz -L https://github.com/actions/runner/releases/download/v2.334.0/actions-runner-linux-x64-2.334.0.tar.gz

# Extract the installer
tar xzf ./actions-runner-linux-x64-2.334.0.tar.gz

# Configure the Runner
./config.sh --url [https://github.com/YOUR-USERNAME/YOUR-REPO](https://github.com/YOUR-USERNAME/YOUR-REPO) --token YOUR_REGISTRATION_TOKEN

Follow on-secreen prompts to name your runner and assign any custom labels.

# Install and Run as a Background Service

sudo ./svc.sh install

# Start the background service
sudo ./svc.sh start

# Verify the service is running successfully
sudo ./svc.sh status
```

### 2. Define the Custom ClusterClass with Automated Patches

ClusterClass uses CAPI patches to automatically fetch the secret, write it out to `/etc/kubernetes/authentication-config.yaml` on control plane boot via cloud-init/kubeadm, and modify the `kube-apiserver` command-line flags without manual intervention:

```yaml
kubectl apply -f vks-github-cicd/infrastructure/custom-v3.4.0-external-oidc.yaml

```

### 3. VKS Authentication Configuration 
Deploy this secret inside vSphere namespace ( infrastructure/cluster-oidc-secret.yaml ) where you would deploy VKS Cluster (eq . `test-namespace`). It configures the API server's token validation parameters using a Common Expression Language (CEL) expression to stay 100% modular across infrastructure forks:

```yaml
kubectl apply -f vks-github-cicd/infrastructure/cluster-oidc-secret.yaml
```


### 4. Instantiate the VKS Cluster

Deploy your guest cluster using the created Custom ClusterClass. The automated hooks in the class handle the deployment configurations down to the underlying compute infrastructure

```yaml
kubectl apply -f vks-github-cicd/infrastructure/cluster-oidc.yaml
```


### 5 Streamlined Cluster Role binding

Instead of tracking individual, transient branches or single user accounts, permissions are bound directly to the dynamic group string generated by the CEL expression

```yaml
kubectl apply -f vks-github-cicd/infrastructure/clusterrolebinding.yaml
```


### 6. Required Repository Secrets
Ensure the following variables are configured in your GitHub Repository under Settings > Secrets and Variables > Actions:
* K8S_API_URL: The private control plane or network load balancer IP address endpoint of your VKS API Server (e.g., https://172.26.0.3:6443).
* TODO_PASSWORD: The encrypted secure state credential injected into your application containers at runtime by Helm.

## Github Pipeline Workflow Matrix


The workflow triggers adaptively depending on where you are in the feature lifecycle:

| Lifecycle Action | Pipeline Trigger | Deployment Environment | Notification Feedback Target |
| :--- | :--- | :--- | :--- |
| **Terminal git push (No PR)** | Completely Silenced | None *(Avoids noise)* | None |
| **Opening / Syncing a PR** |  `pull_request` event | Ephemeral Preview (`pr-X`) | Dual-Post: PR Conversation Timeline **AND** Individual Commit Page History |
| **Merging PR to Main** | `push` to `main` event | Production Live Line (`main`) | Core Commit Log Page History |

## Local Development Lifecycle Guide

### 1. Working on a Feature Preview Environment

```bash
# Spin off a fresh feature branch
git checkout -b feature/preview-test

# Make your application edits, commit, and push upstream
echo "# Adding feature metrics" >> README.md
git add .
git commit -m "feat: adding monitoring layers" -s
git push origin feature/preview-test
```

Note: The pipeline remains silent on this initial push. Head directly to the GitHub web UI to open your Pull Request.

### 2.  Monitoring the Live URLs
* Once your Pull Request is opened, the pipeline kicks off instantly. After compilation and VKS deployment conclude, check:
* The PR Conversation Tab: For the live clickable routing card (http://pr-X.sfo.rainpole.io).
* The Commit Log Tab: For the matching permanent engineering audit link.

### 3. Syncing with Main Post-Merge
Once your PR has been approved and merged via the GitHub interface, clean up your local console workspace to match the remote source of truth:

```bash
# Switch back to your local production tracking track
git checkout main

# Synchronize the fresh merge history containing your new commits
git pull origin main

# Delete the temporary local branch safely
git branch -d feature/preview-test

# Prune disconnected remote tracking pointers
git fetch --prune
```
